# Hybrid rendering: native passes inside paraLLEl-GS

Decided by the user on 2026-10-26, after the measurements of [performance plan](../ee/PERFORMANCE_PLAN.md) item 4d: of three hybrid forms (native fights with paraLLEl-GS for everything else; native passes inside paraLLEl-GS; native 3D with paraLLEl-GS for the HUD and post-processing), the second, with whole native fights as a possible later step. paraLLEl-GS stays the renderer of every frame and the reference; chosen sequences of the game's GS drawing are run instead by GPU passes written for them, which read and write paraLLEl-GS's own GS memory, its super-samples included. Every other draw is emulated as before.

## Why

- **Speed:** at 16x with 60 fps the super attack of the CPU fight (an Angry Kamehameha, about 70 screens of blended dust and smoke a frame) is GPU-bound: 27.6 flips per second. paraLLEl-GS's time is mostly fixed per frame (16x costs twice 1x, not sixteen times) and it shades each layer as the GS would, one primitive after another per tile; a GPU's own rasterizer and blending draw such layers at a small part of that.
- **Quality:** some of the game's effects work in whole game pixels, and no rule of sampling makes them sharper at a higher resolution: the ink outline (an edge filter over material ids, widened by copies one game pixel apart) is either the game's own band or broken into thin lines ([image quality plan](IMAGE_QUALITY_PLAN.md) steps 4 and 5). A pass written for the effect can compute it per sample at the original's thickness.
- **Safety:** the game keeps running on the emulated GS; a native pass covers one known sequence, is switched off by a setting, and is checked against the emulated result.

## How a native pass works

- **Recognition:** by what the GS receives, never by guest PCs or call counts: a sequence of draws with its frame and texture buffers, formats, offsets and blend modes, found as the GIF dump tools showed it (`BT2_GIF_DUMP`, `tools/graphics/gpu/gif_dump_draws.py`). Built at paraLLEl-GS's render passes (`parallel_gs_native_passes.patch`, `runtime/gs/gpu/native/`): each pass classifies a draw by the GS registers when the state changed (`native_draw_kind`), and paraLLEl-GS starts a new render pass where the kind changes, so a sequence arrives whole; when the render pass is flushed, the pass checks it in full (its primitives, states, buffers and textures as the renderer holds them, `native_render_pass`) and either records its work in the renderer's stream (`record_native_work`) or leaves it to the renderer. Nothing is held back or replayed: the GS registers, page tracking and texture caching are those of the drawn pass. Before drawing, it checks what the effect depends on (the buffers' addresses and formats, the palettes' contents where they carry the effect's parameters) and takes the parameters from the GS state, not from constants.
- **Data:** the pass reads and writes paraLLEl-GS's VRAM buffer in GS layout, the base copy and each super-sample plane (the shaders use paraLLEl-GS's swizzle helpers), so everything after it, emulated or native, sees the same memory the emulated draws would have left. It is recorded into paraLLEl-GS's command stream in order, between its render passes.
- **Exactness:** at 1x (no super-sampling) a native pass must leave GS memory exactly as the emulated draws do (a comparison of `readVram` after the sequence, emulated against native, on the fights of the gate and the battle sweep); at higher resolutions it is checked by pictures, and where it changes the look on purpose (the outline) by the user.
- **Switches:** each pass has a setting for players (on by default once checked) and `BT2_NATIVE_PASSES=<list>` (or `none`) for runs; with all off the renderer is today's. `BT2_GS_MEMORY_HASHES=<file>` writes a hash of GS memory after each flip, for the comparison runs.
- **Both renderers:** the in-between pictures (60 fps) run the same passes, so check mode stays exact.

## Order of work

1. **Groundwork — built 2026-10-26.** The hook in paraLLEl-GS (`tools/graphics/gpu/parallel_gs_native_passes.patch`: `native_draw_kind`, `native_render_pass`, `record_native_work`, `get_vram_size`); the passes in `runtime/gs/gpu/native/` (`native_passes.*`: the list and the switches; one file per pass; GLSL in `shaders/`, compiled into committed headers by `tools/graphics/gpu/build_native_shaders.py`, checked by its test); GS memory as paraLLEl-GS holds it: per 32-bit word the resolved value, the super-sample reference one plane on, sample s at plane s + 2, and a pass leaves each pixel as the renderer's shading would (samples kept only while they differ, resolved in the renderer's order of sums). The check pass `alpha-fill` (off by default): flat sprites that write one alpha over a rectangle of a PSMCT32 frame, as before the ink outline (blending may be on: it changes only the masked colour). Checked: on the CPU fight 6,022 render passes drawn natively in 1,300 flips, GS memory identical to the emulated run after every flip at 1x and at 16x (the resolved plane) and the pictures of three flips identical at 16x; 60 fps check mode exact with the pass in both renderers; a unit test (`bt2-gpu-gs-tests`: the same sprites emulated and native, the same GS memory).
2. **HD outline** (the user's request) — **built 2026-10-27 as the native pass `ink-edges`, on by default (the user's choice of look the same day).**
   - **The game's chain** (decoded exactly at 1x on 2026-10-26 from GS memory dumps between its draws, flip 1,000 of the CPU fight): (a) the frame's alpha (the material ids the 3D draws left) copied into the depth buffer's top byte (`0x1c00`); (b) a PSMCT16 buffer (`0x2a00`) cleared; (c) the ids drawn into it through a PSMCT32 palette (CSM1; R = G = a multiple of 8, B = 0, alpha 0x80; alpha masked); (d) red only: minus the palette value half a pixel up, which samples the same texel, so 0; (e) green only: minus the palette value one pixel to the right, non-zero where the right-hand neighbour's material differs (the edge); (f) to (h) the edge read back into the frame's alpha by copies 2, 0 and 1 rows below (0x30, 0x30, 0x80) and the frame darkened by that alpha (a soft three-row band); (i) the frame's alpha restored from the ids. The game finds edges between horizontal neighbours only and widens them by copies whole pixels apart. The renderer draws (b) to (e) single-sampled (`parallel_gs_super_sampled_effects.patch`), which gives the game's band per game pixel; drawn per sample with the same offsets, the edges are one sample row tall and the copies leave thin separate lines.
   - **The native pass** replaces (b) to (e); the copies and the darkening stay the renderer's. It recognises the render pass by its sprites (whole or half pixel corners; texture coordinates spanning what the corners span, so each draw reads the ids a whole texel away), its T8H texture and CSM1 palette (each texture's TEX0 and the renderer's own sampling rates are in the hook), its blending, masks and clamp, and buffers that do not overlap (`runtime/gs/gpu/native/ink_edges.cpp`). Each sample is computed from the ids of the same sample position (`shaders/ink_edges.comp`); then each edge sample is extended down within its game pixel, so the copies join into a band of the original's thickness that follows the geometry at sample precision, and the samples are resolved as the renderer resolves them (`shaders/ink_edges_resolve.comp`). At 1x the result is the renderer's exactly. Square sampling grids only (1x, 4x, 16x); 2x and 8x stay with the renderer.
   - **Checked:** on the CPU fight 1,225 render passes drawn natively in 1,300 flips at 1x, GS memory identical to the emulated run after every flip; 60 fps check mode pixel-exact at 16x at four flips including the super attack, the pass in both renderers; a unit test of emulated against native GS memory; pictures at 16x beside the renderer's band and the 1x picture (`work/frames/ink-compare-*.png`). Near-horizontal edges stay sparse, as the game's rule gives them at 1x and the renderer at 16x: per sample they show as short bars a sample row apart. A variant that also compared each sample with the one a game pixel above outlined them continuously (with a faint fringe from the game's vertical copies); the user preferred the original's sparse look and accepted the bars (2026-10-27).
   - **Setting:** "HD outline" in the Enhancements screen of the launcher and the in-game menu (from the next start, available with super-sampling; off sets `BT2_NATIVE_PASSES=none`).
3. **The super attack's glow** (the goal: a flat 60 at 16x through the super attack with headroom, the user, 2026-10-26).
   - **Measured (2026-10-27, CPU fight at 16x without HD, `BT2_GPU_PASS_TIMES`):** the main renderer's shading is about 8 ms a frame through the fight, and rises to 17.6 ms between flips 3,310 and 3,400 (the Angry Kamehameha's beam, three seconds), all in one render pass into the frame that grows from 1.3 to 10 ms. At the peak (flip 3,350) the frame holds 45 screens of additive glow inside the scissor, beside 59 of the stage and fighters: 153 four-vertex triangle strips (camera-facing quads), small T8 textures through a palette (32 x 32 to 128 x 128), bilinear, perspective texture coordinates, Gouraud colour, MODULATE, depth test greater-or-equal without depth writes, no alpha test, ALPHA (Cs - 0) x As / 128 + Cd with COLCLAMP. With 60 fps the in-between renderer draws the same glow, which is why the beam drops below 30 flips a second.
   - **Why a native pass fits:** saturated addition of non-negative terms gives the same result in any order, and without depth writes or alpha test nothing depends on the order of the quads; the GPU's rasterizer and blending hardware draw such quads at a small part of paraLLEl-GS's per-sample shading (estimated: 165 million blended samples about 1.2 ms on this card, against 10 ms), plus copies of the frame's samples and depth into images and back (about 30 MB each way at 16x).
   - **Design (proposed, waiting for the user's decision):** a native pass for runs of such draws, split into render passes of their own by `native_draw_kind`: the frame's samples (GS memory, base and sample planes) and the depth buffer copied into a colour and a depth image at the sample resolution; the quads drawn with a vertex and fragment shader (the GS's own texture filter on the palette texture read from GS memory, its MODULATE and the term floor(Cs x As / 128) computed as integers, blended ONE + ONE into an 8-bit target, which saturates exactly); the image written back into GS memory with samples kept only where they differ and resolved as the renderer resolves them.
   - **The decision:** the GPU's interpolation of texture coordinates and colours is not the GS's, so at 1x such a pass is unlikely to be exact (the rule of this plan); differences of one colour level are likely here and there. Options: (a) the pass only with super-sampling, 1x left to the renderer (exact by construction), checked at 16x by pictures and by a tolerance against the emulated draws; (b) keep the rule and leave the beam to the renderer (no gain); (c) look for a cheaper change inside paraLLEl-GS first (its shading of these quads, not measured in detail).
4. **Depth of field and the pause's blur at full resolution** (quality; optional): the blur chain's downscales are at the game's resolution by design; a native pass could blur the super-sampled frame instead. Only if the user wants that look.
5. **Whole native fights** (later, the user's decision): if the passes above cover most of a fight's cost, a native renderer for fights with paraLLEl-GS kept as reference and fallback.

The async compute step of the [performance plan](../ee/PERFORMANCE_PLAN.md) (item 4d: the in-between renderer beside the main one on the GPU) is independent of this plan; it was built first (2026-10-26) and helps every frame.
