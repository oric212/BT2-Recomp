# Online battle

Asked by the user on 2026-11-03: a way to make the two-player battle an online battle. This plan records what was found and proposes a way; the choices marked **Decision** are the user's.

## What the references show

- **BT3 on the PS2 has no online play.** Its main menu keeps a hidden "Dragon Net Battle" row whose handler only plays a sound; its `DragonNet_*.pak` files are 64-byte stubs, and the executable has no network code (`work/references/bt3r/docs/NETMENU.md`). The online play BT3 is known for came with the Wii release, not with the PS2 game BT2 shares its engine with.
- **The BT3 port (bt3r) built its own netplay** (`work/references/bt3r/ps2xRuntime/src/lib/ps2_netplay.cpp`, read for the approach only):
  - **Lockstep over UDP.** Only pad input crosses the network (6 bytes a frame); both machines run the whole game. Each packet repeats the last 8 frames' input, so a lost datagram heals with the next one. An input read on frame F is applied on frame F + delay (1 frame on loopback, 2 on a LAN).
  - **Frame numbers relative to the connection,** because two machines connecting mid-session are at different frame counts.
  - **The host decides the match setup** and stamps it into every packet.
  - **Checksums** of the game state every 60 frames to detect a desync.
  - **Rollback** (a missing remote input predicted, the game rewound and re-run when it was wrong), which needed save states of guest memory, devices, kernel records and every guest fiber's stack; and a **state sync at connect** that sends the host's state over TCP.
  - **Their menu entry was retired** (`docs/NEW-NETMENU.md`): routing the hidden row into the game's own Duel state while a custom page owned the screen and the pad could not both hold; the transport stayed.

## What BT2's port already gives (measured 2026-11-03)

- **Determinism.** Two runs of the CPU fight with the window, sound on the audio device, fast loading, pacing and 60 fps agree on all 3,385 fields of the state hash (EE RAM, scratchpad, VU memory). Timers are logical (counted in fields), sound streams advance per field (`services/cri_audio.h`), no real-time clock is read; the host clock only stamps memory card files.
- **Graphics settings do not change the fight.** Between 16x with HD and 1x without, the state differs from flip 173 only in the two 340 KB buffers the game reads back from the GS; at field 3,000 everything else is equal. A desync check must leave out memory written by GS readbacks.
- **Game patches change memory** (the widescreen patch: from field 1), **but not the fight.**
- **The pad seam.** The pad service asks for each port's input once per field (`EeRuntime::on_pad_input`, `on_pad2_input`). Lockstep supplies both ports' input for each field on both machines.
- **Guest threads run on Windows fibers** (`ee/retained_ee_stack.cpp`), the model bt3r's rollback snapshots needed; BT2's port has no save states.
- **Not there yet:** a second controller in a player's session (port 2 is answered as empty outside tool runs), so local two-player is a first step too.

## The user's requirement (2026-11-03): each player keeps their own patches and save

Nothing is transferred: each machine keeps its own game patches, enhancements and memory card. Lockstep only needs the **fight** to be computed alike, not all of memory, so this was measured with the fight's mixed audio, which comes only from the game's own sound commands (every hit, voice and move at its moment) and is byte-identical exactly when the fight goes the same way:

- **Widescreen patch on against off** (the CPU fight, `BT2_START_BATTLE=0,1,0`, 3,000 flips, 106 s of audio): byte-identical. The memory that differs is drawing data: the projections (577.3 against 433, the 4:3 to 16:9 factor), the display lists, the GS readback buffers.
- **The user's own save copied in against a new game's data:** byte-identical.
- **Graphics settings** (16x with HD against 1x), **fast loading, 60 fps, sound on the device:** only the readback buffers differ (above).
- **The control:** the opponent's CPU level 3 instead of 2 changes the audio from 26.8 s on, so the audio does follow the fight.

**So it is possible, with one condition: both machines enter the match the same way, from a fresh start,** not through each player's own menus and save: the game takes random seeds when the battle loads (from Timer 2, counted in fields since the boot), and different menus, saves or loading would give different seeds and a different heap.

**The user's choice (2026-11-03): the game's own screens, everything unlocked.** Picking fighters outside the game would mean one place setting up both sides; instead both machines start fresh straight into the Dueling screen (mode 30, as the tool `BT2_START_SCREEN=30` does: no card check, logos or films) and run in lockstep from there, so the players choose "1P vs 2P", their fighters on the game's own select screen (both cursors, as on the console), the stage and the settings, each with their own controller. - **Desync check without the whole state:** a hash of the game's sound commands (or of the fight's own state once its addresses are known), since memory hashes differ by design between players' settings.
- **Patches that change gameplay** (none today; the widescreen patch is drawing only) would have to match; each patch is marked as drawing or gameplay, and a session refuses mismatched gameplay patches.
- **Not covered yet:** fighters customized with Z-items in versus (their equipment would cross as part of the choice, a few bytes, if the direct start takes it).

## Proposed way

1. **Local two-player.** Port 2 connected in the player's game, with the second controller (or keyboard half) mapped in the launcher and the in-game menu. The game's own "1P vs 2P" then works as on the console. Checked by playing. **Built 2026-11-03:** the setting "Player 2 controller" (Controls, off by default, from the next start) connects port 2 in the player's game: with two gamepads or more the second plays port 2, with one gamepad the keyboard does (`assignPlayers`, `host/input_mapping.h`; `HostInput::gamepads`, `PlayerSession::pad2Input`); the in-game menu and fast forward stay player 1's. Tests: the assignment and the setting's text form. Not yet played by the user.
2. **Lockstep online, from a fresh start into the Dueling screen.** Host and joiner connect in the launcher; both machines start fresh straight into the Dueling screen with every fighter unlocked, each with its own patches and enhancements, and run in lockstep from field 0 there. Port 1 is the host's controller, port 2 the joiner's. Per field each side sends its input (with the last 8 repeated) and waits for the other's input of that field minus the delay; the pacer's wait becomes that wait. Input delay chosen from the measured round trip (16.7 ms a field). Every 60 fields both sides exchange a hash of the fight (the sound commands so far); a mismatch stops the session with a clear message (no faked continuation). Fast forward and fast loading are off in a session. Host and join from the launcher (host: a port; join: address and port), direct UDP.
   Checks: two probes on one PC over loopback with scripted pads and different patches and settings, their fight hashes equal; dropped and delayed packets (a test transport); a forced difference caught by the hash; then the user's two machines.
   **Built 2026-11-04** (below); left: the user's two machines.
3. **Getting through home routers.** Direct UDP needs the host's port forwarded. UPnP port mapping on the host, or a relay server, is a later step.
4. **Rollback.** Save states of the whole game (guest memory, fibers' stacks, every native service's state), taken every field and restored to re-run with the right input. It hides the input delay over long distances; it is large work, after lockstep has proven the game stays in step.

## The lockstep transport (built 2026-11-04)

As designed on 2026-11-03, with these differences: each packet repeats every input the other side has not confirmed (it says how many of the other's inputs it holds), not a fixed last 8; the field count is the session's own count of pad fields (the same on both machines); settings that change the fight are part of the greeting.

- **Where:** `runtime/host/net_lockstep.*`: the lockstep (`Lockstep`) over an abstract transport, and Winsock UDP (IPv4); `runtime/probe/online_session.*`: `BT2_NET=host:<port>` or `join:<address>:<port>`, `BT2_NET_DELAY=<fields>` (0 to 8, default 2). A session sets the rest itself, before anything reads it: the fresh start into Dueling with the menus' sides kept (`BT2_START_SCREEN=30`, `BT2_START_SCREEN_PLAYERS=1`), `BT2_UNLOCK_ROSTER=1`, `BT2_ONLINE_VIEW` (host 1, joiner 2), no card, fast forward, fast loading and the quick title off; other starts and port 2's scripts or live input are refused.
- **Connecting:** the joiner greets every 100 ms until the host answers; the greeting carries the running program's hash (the runtime program's file) and the settings that change the fight (today "Beam struggles by buttons"). A different build or different such settings are refused by both, by name. The host answers every greeting (with its input delay, or none for Auto); over six answers the joiner measures the round trip and, for Auto, chooses the delay: the fastest answer as the link's round trip, the middle one's lead over it as its spread, `Lockstep::delayFor` (half the round trip, half the spread and 2 ms, in fields, and one field more: 2 at home, 3 at 60 ms, 5 at 80 ms with jitter, at most 8). It then starts the session with that delay (start, answered by go). The host takes the first greeting in the protocol's format, and a new one once that sender has been silent for a second (a joiner that started again).
- **Each field:** the pad service asks port 2 first, and that call exchanges: the local input is kept for the field `delay` later and sent; the field waits for the other player's input (resending every 10 ms). Port 1 plays the host's input, port 2 the joiner's; the first `delay` fields are neutral on both.
- **Drift check:** `EeRuntime::service_request_hash` (`services/sif_rpc.cpp`): every native service request's server, function, size and sent bytes, hashed in order while a session runs. Each side sends its latest check (every 60 fields) in every packet; a difference stops both, each saying so ("the two games went apart by field N").
- **Ends:** a player leaving (their program ends, or Escape in a player's game) tells the other ("the other player left the session"); 5 s without a packet ends a session ("no word from the other player").
- **The player's side** (as short as BT3-Recomp's netplay tab, `work/references/bt3r/.../ps2_settings_overlay.cpp`: Host, Join, a remembered address, one status line; the user asked on 2026-11-09 for the online setup as simple as possible): the launcher's "Online battle" has Host a battle, Join with a code and Options (Port, Input delay, Auto by default, Open the port by UPnP). **Host:** one press; the window shows "Waiting for the other player", the code to give, **copied to the clipboard by itself** once known (the internet code from STUN, else the home code), the line asking for the friend's reply code (below, "Without an open port"), the home code when it is another, and Cancel. Confirm or Ctrl+C copies again; the copied code is marked. **Join:** a code already on the clipboard is filled in (`host/clipboard.h` finds it in a chat line), so Join is one press and Enter; Ctrl+V or Shift+Insert pastes one, an address works too. The joiner's window shows its reply code (copied by itself), the host it calls and Cancel, with what to check after a while. The player's guide: `docs/guides/release/ONLINE_SETUP.md`. In a session there is no fast forward, and the in-game menu's keys open the online menu (Resume, End online battle; both games stand still meanwhile, see "Playing online"). Outside fights a line tells each player their side ("you are 2P, the bottom row and the right side"; the user found the two-player select screen unclear); a field that waits over a quarter of a second says so over the last picture, and the window stays answering (closing it leaves the battle); while the game runs over 5% slow with a tenth of its time waiting, a line says the connection is slow. Afterwards the launcher returns, with why the battle ended when it did not end by the player's own choice. A UPnP failure's reason goes to the log. Settings `online_port` (7411), `online_address` (a code or an address), `online_delay` (0: Auto), `online_upnp` (on).
- **Connection codes** (`host/connection_code.h`, the user's request for something seamless): the host's IPv4 address in eight characters ("SC07-3ZKY"; Crockford base32, an 8-bit check over address and port that refuses a mistyped code but one in 256), four more for a port other than 7411. No server: the code is the address. The internet code comes from the router's address by UPnP; an address that providers share (100.64/10, carrier NAT) or a private one gets no code, with the reason. `BT2_NET=join:<code>` takes one too.
- **UPnP** (`host/upnp_port.*`, Windows' NAT traversal API): the host asks the router to open its UDP port on a thread of its own, and closes it again when the session ends. Not yet tried against a router (it changes the router's settings; the user's two machines are the first try).
- **Pacing:** a field that waited for the other player moves the pacer's later deadlines by the wait and 6 ms (`FramePacer::delayBy`): the side ahead then sits a little behind the edge where the other's input just arrives.
- **Leaving:** the other player is told from an exit handler, before the renderer's ending.

## Without an open port (2026-11-09)

**The user's first try between two homes:** the friend joined with the host's code and nothing came; the host's log: "UPnP: no answer from the router". The user asked for no port forwarding at all, self-hosted (no server), simple enough for anyone.

**Evidence (the host's PC):**
- The router (a provider's Vantiva gateway) answers UPnP only with its Wi-Fi setup service (WPS, `WFAWLANConfig`): no port mapping service (`WANIPConnection`) and no NAT-PMP or PCP answer. No program can open a port on it.
- The PC's network is set to Public in Windows, where the firewall also drops the router's multicast UPnP replies (a direct unicast search got the answer above).
- STUN from one socket to three servers (Google, Cloudflare): the same public address and the local port kept (endpoint-independent mapping); not a shared (carrier NAT) address.
- A server answering from another port of the same address (RFC 3489 change request): blocked. So packets get in only from an address this PC has sent to: the host must learn the joiner's address. Without a server between the players, the joiner has to send it back.
- This router does not loop its own outside address back (two sockets of this PC through it: blocked with and without the punch), so a test between two homes is the user's.

**Built:** STUN on the session's own socket (`host/stun.h`, `UdpTransport`: Google's and Cloudflare's servers every half second for 10 s, in a player's game or with `BT2_NET_STUN=1`), so the host's code is its address and port as the internet sees them, whatever the router; UPnP stays as a fallback for the address only. The joiner's window shows a **reply code** (its own address and port, the same code format), copied by itself; the host's waiting screen reads the clipboard twice a second and, on a reply code that is not its own, sends punch packets (`BT2P`, dropped by the receiving transport) to that address every 100 ms until the joiner is heard: the host's router and firewall then let the joiner's greetings in. A home-network host needs no reply. The player's steps: the host pastes the code into a chat; the friend joins (the code fills in) and pastes the reply; the host copies the reply. Tests: STUN messages (both address forms, other transactions, errors, damage), punch packets sent and dropped over UDP on this PC, the screens; with `BT2_TEST_STUN=1` the transport found this PC's address from the real servers. **The first try between two homes failed (2026-11-09):** the host's log: the reply code received, punches sent to 37.142.148.4 port 52695; nothing came back. The joiner's log: greeting the host's 46.121.242.103:7411, no answer. The host's firewall allows the game on Public networks, so the joiner's router most likely gave the host another port than the STUN servers (a router that gives each destination a new port), which the host's router, open only for the exact address and port it sent to, drops.

**The birthday technique (built 2026-11-09, after Tailscale's "How NAT traversal works", 2020, the case of an "easy" and a "hard" NAT):** the hard side opens 256 ports that each send to the easy side's fixed address, so its router holds 256 mappings; the easy side sends to random ports of the hard side's address, each send opening its own router for that port, until one lands on a mapping. The article's numbers for 256 ports: 1,024 probes 98%, 2,048 99.9%; two hard sides need minutes to hours (a relay then). Built in `UdpTransport`: a code marks an IPv4 address behind a router that changes ports (kind byte 5, `Address::changes_port`, from the two STUN ports differing); the side whose router changes ports opens 256 sockets when the other's IPv4 address is easy and sends from each once a second; the other side probes 250 random ports a second (1024 to 65535) of a marked address; sockets are watched with `WSAPoll` (more than `select`'s 64); the first game packet that gets through decides the address and socket, and the other opened ports close. Works whichever side hosts. The prediction and the port window are gone. Tests: a code's mark kept; on this PC a joiner told its router changes ports answered on one of its opened ports, and a host told so found by the joiner's random probes in 0.8 to 1.6 s (five runs). Not yet tried between two homes.

## Playing online (2026-11-09, the user's first battles between two homes)

The battle worked between the two homes. The user's next report, and what was done:

- **Minimizing froze the game.** A game alone survives minimizing (measured: a windowed fight minimized 10 s kept running, 7.3 s of processor time, and was restored), and so did a scripted online pair with the host minimized 15 s (85 drift checks alike). A player's game differs: a field waiting for the other player draws the waiting line by repeating the last picture at its old size (`showAgain`), and a minimized window has no area to present to. The presenter now skips every picture while its window is minimized (`GpuWindowPresenter::present`, `IsIconic`); the game goes on.
- **Button presses did not register before that.** Input was taken only while the game's window had the focus, and online the players are in a chat when the battle starts. Online, the controller now counts while the window is in the background; the keyboard still only with the focus (typing in the chat must not play). The window flashes in the taskbar when the battle connects (`ViewerWindow::attention`).
- **An in-game menu online.** The menu's keys left the battle at once. Now they open the online menu: Resume and End online battle (confirmed; the other player is told, back to the launcher). Both games stand still meanwhile: `Lockstep::keepAlive` (every 100 ms) resends this side's inputs and takes the other's packets, so the other game waits and says so instead of ending the session after 5 s of silence, and this side learns when the other leaves. Measured: a player's game as host, the menu open 8 s by `BT2_PAUSE_TEST=1500:8000` (which opens the online menu in a session), a scripted joiner: both played to the end, 37 drift checks alike, the joiner's wait 8 s longer than without the pause.
